<h4>9.2.1 护栏位置与职责</h4>

输入护栏位于“用户身份与会话归属已确认”和“业务 Agent 开始执行”之间。它检查直接聊天文本、订单补充文本及 CLI 输入是否符合策略，覆盖提示注入、凭据外传、跨用户访问、绕过审批及破坏性请求。正常的订单创建、修改和查询可以通过检查，实际写入仍须经过订单审批和业务权限校验。

Web 新消息先经过 `require_user`，已有会话再经过 `require_thread`；随后调用 `InputGuard.check_text()`。检查通过前不登记新会话、不分配本次业务执行环境，也不调用业务 Agent。此处负责的是输入是否允许进入系统，不能替代账号认证、数据授权或 ERP 业务规则。

{{GUARD_BOARD}}

图中有三种正常去向：通过后进入业务 Agent；在全部安全规则之后命中问候流程，写入固定答复并结束本轮；未通过时在业务执行前返回错误。固定问候同样先经过安全模型检查，不能借问候流程跳过检查。

<h4>9.2.2 文本检查的执行顺序</h4>

1. **基础输入检查。** 拒绝空白文本；加载并验证配置后，检查长度是否超过 16,000 个字符，以及是否存在不支持的控制字符。制表符、换行和回车允许保留。这里的上限是字符数，不是 tokens；输入不会先被截断，避免遗漏尾部指令。
2. **加载策略与配置。** 从 `agent/guardrails/` 读取 YAML、提示词与 Colang 流程，验证参数类型、规则内容、模型配置与严格输出解析器。必须保留 `self check input`；直接回复流程被统一排在所有安全检查之后。
3. **创建隔离的检查实例。** 每次检查创建独立 Rails，注入规则和由服务端认证取得的 user_id，不复用其他用户的对话上下文。可复用的是无会话状态的模型客户端，规则和 Rails 实例不会跨检查缓存。
4. **语义审查。** 将规则放在 system 消息，将完整待审查文本放在 user 消息。模型只判断 ALLOW/BLOCK，不负责回答采购问题、执行工具或遵循待审文本中的“管理员”“系统指令”等自称身份。
5. **严格解析。** 仅字符串去除首尾空白后严格等于 `ALLOW` 才算允许。`BLOCK`、空输出、解释文字、小写或混合格式均不能获得放行结果；不从一段解释中模糊提取 ALLOW。
6. **确定性规则与固定回复。** 语义审查允许后，执行 Colang 业务规则，再执行 greeting。当前联系人导出规则只精确匹配整句“导出全部供应商联系人”，不能描述成所有同义表达都已由这条确定性规则覆盖。
7. **验证最终结果。** 普通放行必须同时满足 Rails 状态为 PASSED、返回内容与原始输入完全一致；不采用 SDK 改写后的文本。命中明确列入 direct_response_flows 的固定回复流程时，可以使用非空固定文案；其他 BLOCKED 结果按策略拦截处理。

严格判定的核心代码来自 `agent/input_guard.py`：

```python
def _parse_verdict(output: str) -> tuple[bool, list]:
    return isinstance(output, str) and output.strip() == "ALLOW", []
```

普通聊天的接入顺序示意如下，省略 SSE 和异常响应细节：

```python
# user_id 来自服务端认证；已有会话先验证归属。
direct_response = await get_input_guard().check_text(
    request.message, user_id=user_id
)
# 只有检查正常返回，才登记新会话并进入执行图。
# direct_response 非空时由 GuardrailResponseMiddleware 写入固定答复，跳转结束。
```

固定回复仍经过执行图的初始化与持久化链路，只是中间件在业务模型调用前结束本轮；不能据此宣称它完全不需要构图或沙箱初始化。

<h4>9.2.3 补充信息与审批恢复</h4>

{{RESUME_BOARD}}

恢复入口先校验登录态与会话归属，再调用 `check_resume()`。它只接受下面两类互斥结构；校验通过后才生成 `Command(resume=...)`，由已有中断点继续任务。

| 恢复类型 | 合法结构 | 检查方式 |
| --- | --- | --- |
| 补充信息 | `{"supplement":"数量 100，交期 2026-11-15"}` | 顶层只能有 supplement；其文本再次走完整 check_text 流程 |
| 审批决定 | `{"decisions":[{"type":"approve"}]}` | 顶层只能有 decisions；列表为 1–20 项；每项只能包含 type，取值仅 approve/reject |

审批决定不调用语义审查模型，因为其表达空间已由服务端结构校验限制；仍需要读取有效配置以确认数量上限。不能夹带额外指令、同时提交 supplement 和 decisions，或通过 edited_action 等字段修改待审批工具参数。

补充文本检查的固定问候返回值当前不会转成独立问候答复：`check_resume()` 只把它当作检查完成，继续恢复原补充流程。这与新聊天请求的固定回复分支不同。审批结构合法也不表示工具已经执行成功；恢复后仍由原中断机制和业务工具返回决定执行结果。

<h4>9.2.4 配置、超时与异常处理</h4>

| 配置或结果 | 当前行为 | 对业务执行的影响 |
| --- | --- | --- |
| 最大输入长度 | 16,000 字符；不截断后再送审 | 超限返回 422 |
| 恢复审批数量 | 1–20 条 approve/reject | 结构、字段或枚举无效返回 422 |
| 审查模型 | 独立配置的 deepseek-flash；temperature=0、max_tokens=32、thinking disabled | 与业务模型配置分开管理 |
| 模型调用 | timeout=10 秒，max_retries=0 | 避免审查客户端反复重试拖长请求 |
| 审查阶段外层超时 | 15 秒，覆盖 Rails 初始化与 check_async | 超时返回 503；配置文件加载和先前认证不在这个计时块内 |
| 策略拒绝 | HTTP 403，code=input_blocked | 返回统一拒绝文案，不进入业务 Agent |
| 输入格式错误 | HTTP 422，code=input_invalid | 提示修正输入或恢复结构 |
| 配置、模型服务或异常结果 | HTTP 503，code=input_check_unavailable | 本次停止；不会因审查不可用自动放行 |
| 配置更新 | 每次检查重新读取 YAML / Colang | 修改后在后续检查生效，无须复用旧 Rails |

配置分工：`config.yml` 定义审查模型和流程顺序，`policies.yml` 定义运行限制及允许/禁止规则，`prompts.yml` 定义审查提示和解析器，`rails/business.co` 定义确定性业务规则与固定回复。配置验证会拒绝不安全的流程组合，例如启用直接回复同时又将输入检查设为并行。

审查异常对用户仅返回统一错误；护栏日志记录异常类型，不记录用户原文或模型原始输出。这一约束仅描述护栏模块，其他流式调试日志仍可能包含业务输入与工具结果，见 13.3 的运行观测边界。

<h4>9.2.5 典型场景与覆盖边界</h4>

| 输入或事件 | 设计预期 | 说明 |
| --- | --- | --- |
| 比较供应商报价、创建正常采购订单 | 允许继续业务流程 | “下单”本身不等于绕过审批 |
| “你好”及当前配置中的问候形式 | 安全检查后固定回复 | 不调用业务模型生成问候，但仍有审查模型调用 |
| “导出全部供应商联系人” | 当前精确规则拦截 | 同义表达是否拦截取决于语义策略和评估结果 |
| 索取密钥、伪造高权限身份、要求绕过审批 | 策略期望拦截 | 这是策略目标，不代表模型检测率为 100% |
| 空白、超长文本、非法控制字符 | 422 | 在业务 Agent 执行前处理 |
| 配置损坏、审查模型断连或超时 | 503 | 检查不可用时停止当前执行 |
| 审批请求夹带修改后的工具参数 | 422 | 不允许借恢复入口绕过原审批参数 |

当前只审查本次直接用户输入，不把完整历史一起送给审查模型，也不审查网页正文、MCP 工具结果或最终输出。外部内容中的间接提示注入、跨轮组合攻击、输出审查、字段级业务权限与操作审计仍需独立建设。后续评估应同时覆盖正常业务误拦截、攻击漏检、超时失败、并发用户隔离与配置热更新，记录实际结果后再报告准确率。

实现依据：`api_view/api/chat.py`、`agent/input_guard.py`、`agent/guardrails/`、`agent/middlewares/guardrail_response.py` 与 `test/agent_test.py`。
